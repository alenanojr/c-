    WPF + XAML Lab
    

    WPF = desktop framework. XAML = UI definition. C# = behavior. Ang key skill ay data binding, commands, layouts, at reusable controls.
    

    Controls cheat sheet
    ControlUseTypical binding
    

    TextBoxUser inputText
    TextBlockDisplay textText
    ButtonActionCommand
    ComboBoxSelect itemItemsSource / SelectedItem
    DataGridTables/listsItemsSource
    GridRows/columnsLayout
    StackPanelSimple stackingLayout
    BorderCard/containerStyle
    

    Two-way binding
    <TextBox
    Text="{Binding Name,
      Mode=TwoWay,
      UpdateSourceTrigger=PropertyChanged}" />
    Habang nagta-type ang user, napupunta ang value sa ViewModel.
    

    DataGrid
    <DataGrid
    ItemsSource="{Binding Employees}"
    AutoGenerateColumns="True" />
    Karaniwang ObservableCollection ang source para automatic ang add/remove notification.
    

    Code-behind vs MVVM
    // Avoid putting business rules here:
private void Save_Click(object sender, RoutedEventArgs e)
{
    // lots of business logic...
}

// Prefer:
<Button Content="Save"
        Command="{Binding SaveCommand}" />
    Event handler is not forbidden, pero sa MVVM-heavy app, commands keep UI actions in the ViewModel.
    

    Interview: "XAML describes the view, while bindings and commands connect it to the ViewModel. That keeps UI code separate from business logic."

    Async + Testing + Performance + Security
    

    Ito ang mga topic na madalas nagpapakita kung marunong ka sa production software, hindi lang sa syntax.
    

    

    async / await
    public async Task<Employee> GetEmployeeAsync(int id)
{
    return await db.Employees
        .FirstOrDefaultAsync(e => e.Id == id);
}
    Huwag i-block ang UI thread habang naghihintay ng database/API.
    

    UI thread
    Serial DataReceived
       ↓
background thread
       ↓
Dispatcher
       ↓
ViewModel / UI
    Hardware callbacks can happen off the UI thread.
    

    

    Testing pyramid
    Unit test
  ↓
Service / integration test
  ↓
UI / end-to-end test
    Unit tests should be fast and isolated. Mock hardware/API dependencies when practical.
    

    Example unit test
    [Fact]
public void Parser_ParsesTemperature()
{
    var ok = TemperatureParser.TryParse(
        "TEMP:28.5", out var value);

    Assert.True(ok);
    Assert.Equal(28.5, value);
}
    

    Performance checklist
    Database: indexes, pagination, efficient queries, AsNoTracking() for read-only EF queries. UI: don't block the UI thread; use virtualization for large lists. API: async calls, caching where appropriate, timeouts and retries. Hardware: avoid excessive polling and unnecessary serial traffic.
    

    Security checklist
    Parameterized queries/EF Core → SQL injection protection. HTTPS → transport security. Passwords → proper hashing, never plain text. API keys → environment/secret store, never hardcode in Git. Input validation → reject malformed or unexpected data. LLM output → validate before using it to trigger commands, SQL, or device actions.
    

    Interview: "When debugging, I reproduce the issue, isolate the layer, inspect logs and breakpoints, identify the root cause, fix it, then retest and add regression coverage when appropriate."
